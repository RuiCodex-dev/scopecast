A snapshot of the code at commit 7f58179 plus later video and docs commits (2026-10-15). It can drift as the code changes.

What the app is

A single web page for freelance developers. You paste a client's feature list, give every task a range of hours, and Scopecast simulates the project 10,000 times to quote a fixed price at the confidence level you choose. When the client's budget is lower, it suggests which tasks to move to a phase 2. Everything runs in the browser; the project is saved in local storage.

Four pieces: the engine (pure TypeScript: parse, estimate, simulate, fit), the store (one reducer plus autosave), the forecast hook (turns tasks into simulated totals), and the UI (workbench and client quote).

One action, end to end: moving the confidence dial

Reference route (three stops)

A reference route through the real code; it was not toured live with the owner.

  1. Input — src/components/ForecastPanel.tsx, search id="confidence". The range input dispatches { type: 'setConfidence' }; src/state/store.ts snaps it to steps of 5 between 50 and 95.
  2. Logic — src/state/useForecast.ts, function useForecast. Per-task samples are cached by task id and range; phase-1 samples are summed run by run and sorted once by summarize() in src/engine/simulate.ts. The dial only changes p, so phase1.at(p) is a lookup.
  3. Result — priceFor() in src/state/useForecast.ts (hours × rate, rounded up to €50) and src/components/ForecastCurve.tsx, which draws the terracotta marker at summary.at(p).

A practice to reuse

Turn a vague requirement into a check that can fail. The PRD said the budget fitter should "defer as little estimated work as it can" (devpost/prd.md → Fitting a client budget). The first versions (a greedy pass, then a subset-sum shortcut) looked right in the UI, but the test defers close to the least expected work, checked against every subset in src/engine/engine.test.ts compared it with a brute-force answer and failed: it deferred about 22 expected hours where 18 were enough. The fix (a best-first search) is recorded under Revisions in devpost/checklist.md.

On another project: when a requirement contains "as little as", "fast" or "smooth", write the comparison that would prove it wrong before trusting the implementation.
